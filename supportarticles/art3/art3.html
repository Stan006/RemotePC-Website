Article: Windows Security Model

Why Windows blocks drag and drop between privilege levels

This behavior is enforced by User Account Control (UAC) and Mandatory Integrity Control (MIC) to prevent privilege escalation.

Integrity Level Separation

Windows assigns an integrity level to every process. This level determines what other processes it can interact with. The key rule enforced by the system is:

Lower integrity processes cannot send data to higher integrity processes ("no write up").

Even though both applications belong to the same user, Windows treats them as different trust boundaries.

What actually gets blocked

Drag and drop is not just a UI feature — it relies on multiple IPC mechanisms:

  • Window messages (e.g. WM_DROPFILES)
  • OLE drag-and-drop via IDropTarget
  • COM data transfer between processes

These mechanisms require one process to send structured data into another process's context. When integrity levels differ, Windows blocks this interaction at the kernel and user32 boundary.

Relevant Windows APIs

There are APIs that relate to message filtering, but they do not bypass integrity isolation:

  • ChangeWindowMessageFilterEx – allows specific messages through, but only within limits
  • AllowSetForegroundWindow – unrelated to drag/drop but often confused
  • CoInitializeSecurity – controls COM security boundaries

Importantly, ChangeWindowMessageFilterEx cannot override MIC restrictions for drag-and-drop data transfer.

We are currently looking for ways to make it work, however due to the described security lockdowns, a solution will delayed for the future, or indefinitely.

Why Microsoft enforces this

If drag and drop were allowed freely across privilege levels, it would enable:

  • Shatter attacks via crafted window messages
  • Data injection into elevated processes
  • Privilege escalation chains

Historically, older versions of Windows (pre-Vista) were vulnerable to these types of attacks, which is why UAC introduced strict isolation.

Why Administrative Privileges Are Required By RemotePC

Accessing system temperature sensors requires administrative privileges because these sensors are part of protected hardware interfaces. Standard user processes do not have permission to read from or interact with these low-level system resources, ensuring that critical hardware data cannot be tampered with or accessed by untrusted applications.

Running the application as an administrator allows it to safely query sensor data directly from the system, providing accurate readings while maintaining Windows security boundaries.

We are currently evaluating whether allowing the application to run as a non-administrative process—controlled via a toggle in the settings—would be a viable option for users. Running in this mode would enable features like drag-and-drop but would disable access to hardware temperature sensors. As a result, temperature readings would not be available in the Android app.

Key Takeaway

Drag and drop is blocked not because of a bug, but because Windows treats it as a cross-process data injection mechanism — which is restricted across integrity boundaries.
